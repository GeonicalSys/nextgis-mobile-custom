# Дорожная карта мобильного приложения ЛИСА и БЕЛКА

Версия от 25 октября 2026 года. Область — мобильные приложения ЛИСА и БЕЛКА, библиотеки maplib и maplibui и необходимые контракты с PostgreSQL и NextGIS Web.

Главный порядок развития: сохранить полевые правки и обеспечить восстановление, ускорить обычную работу с сервером и картой, затем добавить обмен между устройствами без интернета. Удобство улучшаем небольшими самостоятельными задачами параллельно с этой работой.

Карта объединяет три известных направления и дополнительные предложения. «Подтверждено кодом» означает установленное поведение исходников; «риск» требует воспроизведения; «предложение» описывает развитие продукта. Эти отметки не означают, что доработка уже выпущена.

# Правило для любой доработки

Карта согласует работу, но сама по себе не разрешает исполнение всех перечисленных задач, изменение рабочих данных/серверов или выпуск APK. Внедрение регламента не заменяет существующие разрешения и ограничения.

Любое изменение, включая срочное исправление, запрос заказчика и работу стороннего разработчика, связывается с ID этой карты. Если подходящего пункта нет, до начала обычной разработки добавляется новый пункт с причиной, приоритетом, зависимостями и влиянием на текущую очередь. Срочный инцидент можно исправлять сразу; карточка и причина изменения очереди должны появиться до слияния PR.

Владелец продукта согласует изменение приоритетов и объёма. Технический ответственный проверяет данные, совместимость и зависимости. Имена ответственных назначаются при переводе задачи в «Готова к работе». Проходить повторное согласование каждого технического шага внутри принятого объёма не требуется.

Карточка содержит: ID; проблему и пользователя; ожидаемое поведение; основание; приоритет; владельца; репозитории; зависимости; что входит и отложено; критерии приёмки; проверки; ссылки на issue/PR; состояние доставки. Одна задача может иметь несколько PR в разных репозиториях, а один PR — несколько ID.

В PR обязательны ID карты, объяснение связи с целью, влияние на данные/синхронизацию/карту/фон/батарею, выполненные проверки и состояние зависимостей. Для внеплановой работы дополнительно указываются причина срочности и задачи, которые она сдвигает. «Не влияет» сопровождается коротким обоснованием.

## MOB-00 Привязка работы к дорожной карте

Приоритет P1. Состояние: В PR #78; регламент добавлен в документацию, автоматический контроль пока не реализован. Владелец — Android root; бизнес очередь согласует владелец продукта.

Закрепить правило в Android AGENTS.md, docs/START-HERE.md, change-checklist и шаблоне PR. Приёмка: автор обычной и внеплановой доработки может найти карту из стартовых инструкций, указать существующий ID либо добавить новый, объяснить влияние и приложить проверку; ревьюер сверяет смысл и зависимости. Документационная доработка не запускает тяжёлые native проверки сама по себе.

Автоматическую проверку существования ID и обязательных полей выделить следующим шагом: локальный pre-push даёт раннюю обратную связь, серверный PR check охватывает также сторонние и веб-коммиты. Обязательное прохождение check и ревью задаётся правилом слияния целевой ветки; изменение такой настройки требует отдельного полномочия. До внедрения этих мер контроль остаётся регламентом ревью. Один заполненный ID смыслового соответствия не доказывает.

| Этап | Задачи | Результат перехода |
|---|---|---|
| Основа | MOB-00, REL-01, REL-02, PERF-01; текущий MOB-01 учитывается отдельно | Правки не теряются молча, есть путь восстановления и измеримый исходный уровень |
| Первые улучшения | SYNC-01, MVT-01, UX-01, UX-02 | Неизменённые PostgreSQL слои пропускаются безопасно; карта обновляется; пользователь понимает состояние данных |
| Производительность | SYNC-02, MVT-02, REL-03 | Передаются изменения; тайлы и длинные операции укладываются в измеренные бюджеты |
| Проверка офлайн обмена | P2P-01, P2P-02 | Два доверенных устройства обмениваются без интернета и без потери/дублирования операций |
| Распространение через другие устройства | P2P-03 | Повторные встречи и маршруты A → B → C → сервер сходятся к согласованным данным |
| Развитие полевой работы | GEO-01, UX-03, UX-04, EXT-01 | Более понятные измерения и меньше действий в повседневных сценариях |

Этапы задают зависимости, а не календарные обещания. MVT и небольшие UX задачи могут идти параллельно серверной синхронизации. P2P использует общий контракт операций; прототип транспорта можно исследовать раньше, но нельзя выдавать его за готовую синхронизацию.

Состояния: Предложена → Исследуется → Готова к работе → В работе → В PR → Слита → Проверена на устройствах → Выпущена. Дополнительные состояния: Блокирована и Отложена с причиной. Для исследования результатом служит принятое решение; выпуск к нему не применяется. Код в PR, merge, проверка и доступный пользователям APK учитываются отдельно.

P0 — возможная потеря данных или ложное подтверждение успеха; P1 — надёжность основных сценариев и заметная производительность; P2 — удобство и расширение возможностей. Новая функция не должна обходить незакрытую P0 проблему в том же пути.

# Сохранность данных

## REL-01 Достоверное подтверждение отправки

Приоритет P0. Состояние: Исследуется. Основание: подтверждено кодом. Владельцы реализации — maplib, интеграция app/maplibui.

В NGWVectorLayer успешный HTTP ответ создания с JSON без поля id возвращается как успех; вызывающий код после этого удаляет NEW из очереди. При пустом cursor для создания/изменения также действует политика «обработано». Это требует исправления и адресной проверки; потеря данных на конкретном телефоне этим аудитом не установлена.

Приёмка: отсутствующий, неверный и недопустимый server ID не очищает правку; remap локального ID и подтверждение очереди согласованы. Временная ошибка чтения, действительно осиротевшая запись и повреждение БД различаются; неопределённые операции сохраняются для восстановления, обычная очередь продолжает работу.

Отдельно проверить «сервер принял POST, ответ потерялся» и смерть процесса между ответом и локальной фиксацией. Пока backend не даёт подходящей поддержки, нельзя обещать однократное создание при любых повторах. Нужен явный способ сверки неопределённого результата.

Основание: [создание и ACK](https://github.com/GeonicalSys/android_maplib/blob/7e7055e54002b116e7a147fcd2791486913ddd9a/src/main/java/com/nextgis/maplib/map/NGWVectorLayer.java#L3883), [очистка очереди](https://github.com/GeonicalSys/android_maplib/blob/7e7055e54002b116e7a147fcd2791486913ddd9a/src/main/java/com/nextgis/maplib/map/NGWVectorLayer.java#L1357).

## REL-02 Восстановление проекта и сохранение повреждённых черновиков

Приоритет P0 для сохранения оригинала черновика, P1 для полного восстановления. Состояние: Исследуется. Основание: подтверждено кодом и действующим описанием backup.

FeatureFormDraftStore очищает повреждённый/некорректный черновик при чтении. Сначала нужно сохранять исходные байты в карантин и давать повторную попытку или экспорт. Нельзя обещать автоматическое восстановление любого повреждённого содержимого.

LayerBackup format2 уже сохраняет данные слоя и вложения, но не является полным архивом проекта: config/forms/assets включены не полностью, готового универсального restore нет. Нужны проверяемый формат полного архива, совместимость схемы и мастер восстановления на отдельной копии.

Приёмка: проверить архив до destructive действия; восстановить проект офлайн с объектами, геометрией, фото, формами, настройками и несинхронизированными правками. Сравнить ID, значения и хеши вложений. Чужая identity, повреждённый архив, нехватка места и несовместимая версия отклоняются без изменения рабочей копии. Восстановленная очередь не отправляется на сервер до согласованной сверки.

Основание: [FeatureFormDraftStore](https://github.com/GeonicalSys/android_maplibui/blob/ff4a1cce63d11fea864843550173ec22a508d334/src/main/java/com/nextgis/maplibui/util/FeatureFormDraftStore.java#L115), [границы восстановления](https://github.com/GeonicalSys/nextgis-mobile-custom/blob/8cc630ad2abd04d49470ea54715f7f69f9d32618/docs/runbooks/incident-and-rollback.md#L41).

## REL-03 Работа при прерывании и нехватке ресурсов

Приоритет P1. Состояние: Предложена по результатам анализа. Основание: оставшиеся архитектурные расходы и риски.

Потоковая полная синхронизация уже реализована, но хранит крупные наборы ID в памяти; одна огромная геометрия остаётся отдельным риском. Предварительная проверка диска не покрывает весь рост staging, backup и SQLite. Длинный обход сериализует полный checkpoint синхронно в пути GPS callback.

Приёмка: контроль бюджета RAM и временного диска на всех стадиях; безопасный отказ при ENOSPC; отсутствие потери предыдущей базы и очереди. Длинные checkpoint переносятся из чувствительного к задержкам пути с упорядоченной записью и обязательным flush перед Finish. Проверить process kill, reboot, отмену, отзыв разрешения и повторное продолжение. Незавершённая работа остаётся видимой и восстанавливаемой.

Основание: NGWVectorLayer.java, WalkEditService.java, WalkSessionStore.java; подробности и исторические замеры — в mobile-reliability-audit.md. Исторический замер не принимается за производительность текущего APK.

# Ускорение синхронизации с сервером

Основной backend — PostgreSQL. Разрешены доработки нашей базы; расширение NextGIS Web не входит в решение. Для загруженных непосредственно в NGW слоёв нужен отдельный безопасный путь. Встроенное NGW versioning не принимается как обязательная зависимость.

## SYNC-01 Пропуск неизменённых PostgreSQL слоёв

Приоритет P1. Состояние: Предложена; нужен прототип серверного контракта. Зависимости: REL-01 и PERF-01.

Служебный маркер изменения слоя и поколения источника должен учитывать все изменения результата, включая удаления и зависимые таблицы. Проверить возможность чтения служебных данных через обычные разрешённые PostGIS ресурсы и API установленного NGW. Начать с одного настоящего слоя и параллельных транзакций.

Приёмка: неизменённый слой не скачивает объекты; изменённый использует безопасную полную загрузку; исходящие правки отправляются независимо. Изменения атрибута/геометрии при прежнем количестве, delete+insert с прежним количеством, длинная транзакция, смена фильтра/прав/схемы и пересоздание источника не пропускаются. Отсутствие достоверного маркера возвращает к полной проверке.

Количество объектов и время последнего запуска приложения не являются достаточным доказательством актуальности. Протокол отдельно доказывает, что его граница не пропускает поздно завершившиеся транзакции.

## SYNC-02 Получение только изменений

Приоритет P1. Состояние: Предложена. Зависимости: SYNC-01 и принятое решение о конфликтах.

Нужны журнал изменений, удаления, устойчивый cursor по слою и области доступа, ограниченная граница пакета, безопасная загрузка страниц и bootstrap/resync при разрыве истории. Объект, вышедший из фильтра проекта, должен исчезнуть на телефоне как положено.

Приёмка: одинаковый итог после delta и эталонной полной проверки; повтор пакета безопасен; данные и cursor фиксируются вместе; прерывание не продвигает cursor. Локальные правки сохраняются. Для конкурентной правки и update/delete есть явная политика; геометрия не перезаписывается молча. Вложения, формы, настройки и состав проекта имеют собственные версии/проверки.

Сценарий без серверной поддержки сохраняет существующий полный путь с уменьшением повторной работы и измеренными бюджетами. PostgreSQL механизм выбирается после проверки нагрузки и порядка фиксации транзакций; раннее решение «достаточно timestamp или sequence» не принимается без доказательства.

# Векторные тайлы и большие карты

## MVT-01 Корректность и актуальность

Приоритет P1. Состояние: Исследуется. Основание: риск в исходниках.

При обновлении существующего источника используется прежний URL тайлов. Нужно проверить обновление уже видимой области после изменения/удаления объекта и синхронизации, без перезапуска и движения карты. Смена проекта с одинаковыми layer ID также не должна показывать данные другого проекта.

Приёмка: геометрия, подпись и identify согласованы; известна версия данных, по которой построен тайл; принята явная инвалидация. Отдельная матрица покрывает multipart, holes, границы тайлов, тонкие полигоны, подписи, порядок/видимость, смену стиля и lifecycle. Пока воспроизведения нет, устаревшее изображение учитывается как риск, а не установленный пользовательский дефект.

## MVT-02 Производительность и ограниченный кэш

Приоритет P1. Состояние: Предложена. Зависимости: PERF-01 и MVT-01.

Сократить повторное чтение полной геометрии и атрибутов, измерить batch чтение и безопасное упрощение для отображения. Добавить ограниченный RAM/disk кэш с identity проекта, слоя и ревизией данных, а при необходимости — стиля. Общие запросы одного тайла не должны повторять сборку.

Приёмка: повторный просмотр области уменьшает DB/encode работу; sync немедленно делает старый кэш непригодным; быстрый pan/смена проекта отменяют устаревшую активную работу. Бюджеты времени/вершин/байтов соблюдаются без выдачи неполного тайла как успешного. Исходная бизнес геометрия сохраняется.

Уже существуют два worker, очередь 16, защита по свободной heap памяти, сериализация одного слоя и classic fallback. Их нужно сохранить. Расширение на редактируемые слои — отдельное решение после проектирования edit/sync. Обычные стили, custom icons и rule styles продолжают работать через поддерживаемый путь.

Основание: [LocalVectorTileProvider](https://github.com/GeonicalSys/android_maplib/blob/7e7055e54002b116e7a147fcd2791486913ddd9a/src/main/java/com/nextgis/maplib/map/LocalVectorTileProvider.java#L71), [MapDrawable](https://github.com/GeonicalSys/android_maplib/blob/7e7055e54002b116e7a147fcd2791486913ddd9a/src/main/java/com/nextgis/maplib/map/MapDrawable.java#L1424).

# Обмен между устройствами без интернета

Цель из первого обсуждения — доверенные полевые устройства обмениваются при встрече и передают полученные изменения дальше; каждое может позже доставить их серверу. Дальность, скорость и работа с выключенным экраном проверяются на целевом парке устройств.

## P2P-01 Общий протокол операций и доверия

Приоритет P1 для проектирования, после основного online контракта. Состояние: Исследование. Зависимости: REL-01, SYNC-02 либо согласованный эквивалент.

Определить identity проекта/организации/слоя/объекта, UUID операций, порядок/пропуски операций, base revision, tombstones и серверные подтверждения. Доставка соседу и подтверждение сервером — разные состояния. Вложения передаются отдельно по проверяемым хешам, с возобновлением и квотами.

Нужны первичное доверие, взаимная проверка устройства, предел прав на чужие операции, срок действия допуска и отзыв. Постоянный офлайн не позволяет мгновенно узнать серверный отзыв: ограничение и поведение после истечения допуска входят в контракт.

Критический прототип: получить чужую правку на A и доставить её серверу стандартным разрешённым способом с сохранением авторства/прав и защитой от дублей. Пока это не доказано на нашем PostgreSQL/NGW пути, весь обмен не готов к реализации.

## P2P-02 Обмен двух устройств

Приоритет P2 для реализации после протокола. Состояние: Предложена.

Прототип Nearby Connections как одного из транспортов; отдельно решить поддержку устройств без Google Play services. Файловый пакет/локальная Wi-Fi сеть — кандидаты для запасного способа того же протокола, без замены рабочей БД целиком.

Приёмка: устройства без интернета обмениваются после однократного доверенного подключения; незнакомое устройство не получает данные; обрыв, повтор, недостаток места и несовместимая схема безопасны. Проверить фото, конфликт, проверку целостности и одинаковые ID разных проектов.

Nearby предоставляет локальный транспорт, но не готовую репликацию приложения. Фоновые ограничения Android требуют отдельной проверки; постоянная доступность не следует из наличия foreground service. [Nearby overview](https://developers.google.com/nearby/connections/overview), [ограничения Android](https://developer.android.com/develop/background-work/services/fgs/restrictions-bg-start).

## P2P-03 Передача дальше и автоматический режим

Приоритет P2. Состояние: Предложена. Зависимость: принятый P2P-02.

Сначала доказать сценарий A → B → C → сервер, повторную встречу A/C, пропущенные номера, дубли и конфликт update/delete. Потом включать автоматический обмен доверенных устройств с режимами выключен/вручную/автоматически и наблюдаемым расходом батареи.

Приёмка: повторные маршруты сходятся без дублей и потери правок; история не удаляется до достаточного подтверждения; квоты не вытесняют неподтверждённую работу. Свежесть сервера, последняя встреча и прямая связь с сервером различаются; «передано соседу» не означает «принято сервером».

Топология и одновременность передачи выбираются по пилоту. Автоматическое переключение между стратегиями и скорость на 50 метрах не считаются гарантированными. [Официальные стратегии Nearby](https://developers.google.com/nearby/connections/strategies).

# Надёжность измерений

## GEO-01 Понятная оценка GPS и длинный рабочий день

Приоритет P1. Состояние: Исследуется. Основание: подтверждённая семантика усреднения и необходимость полевой приёмки.

AccurateLocationTaker использует разброс накопленных точек как accuracy усреднённой позиции. Кучность не доказывает абсолютную точность. Разделить оценку положения, разброс и свежесть; сохранить происхождение данных встроенного/внешнего приёмника. Ограничение отображения снизу само по себе эту проблему не решает.

Приёмка: статическая и движущаяся проверка с независимой опорой; помещение, лес и открытая местность; временная потеря GPS/внешнего приёмника. Не вводить «95%» простым пересчётом без подтверждённой модели. Отдельно проверить запись полного рабочего дня, screen off, восстановление процесса и расход батареи.

Основание: [AccurateLocationTaker](https://github.com/GeonicalSys/android_maplib/blob/7e7055e54002b116e7a147fcd2791486913ddd9a/src/main/java/com/nextgis/maplib/location/AccurateLocationTaker.java#L173).

# Удобство и расширение функций

Здесь перечислены предложения для проверки с полевыми пользователями. Уже работающие формы, scripts, вынос в натуру, локальные проекты и общие треки не переобъявляются новыми возможностями.

## UX-01 Проверка готовности к выезду

Приоритет P1. Состояние: Предложена.

Один экран отвечает, готов ли выбранный проект к работе без сети: данные и формы на месте, подложка покрывает нужную территорию, есть место на диске, права и GPS доступны, незавершённые операции видны. Показывать конкретную причину и действие «скачать / повторить / открыть настройки».

Приёмка: после подготовки и включения авиарежима выполняется согласованный сценарий просмотра, поиска, формы и фото. Отсутствующая часть не помечается «готово». Проверка не требует от полевого сотрудника знания серверных терминов.

## UX-02 Центр изменений и синхронизации

Приоритет P1. Состояние: Предложена. Использует существующие очередь и статусы.

Показать не только число слоёв с правками, а сами ожидающие объекты/вложения: «сохранено на устройстве», «ожидает отправки», «нужна сверка», «подтверждено сервером». Для сбоя — причина и одна подходящая команда. В P2P добавить отдельный этап доставки через другое устройство.

Приёмка: пользователь может найти конкретную неотправленную правку, понять её судьбу и безопасно повторить. Частичная синхронизация не выглядит полным успехом; повтор не требует заново открывать и пересохранять форму. Простой список выбора проекта остаётся простым — подробности открываются отдельно.

## UX-03 Быстрые полевые действия и офлайн поиск

Приоритет P2. Состояние: Предложена.

Проверить пользу избранных слоёв/действий, последних и закреплённых объектов, сохранённых фильтров и поиска по понятным полям проекта. Это развитие существующих средств поиска и редактирования; сначала сравнить с фактическим рабочим маршрутом. Для большого списка проектов добавить отдельный поиск и избранное, сохраняя простые строки с именами и запрет переключения во время активной записи.

Приёмка: пользователь без сети находит объект по принятому полевому идентификатору, открывает форму, добавляет фото и возвращается к прежней области карты. Вынести частые команды ближе к карте, сохранив отдельные сложные настройки; зафиксировать сокращение шагов относительно текущего сценария.

## UX-04 Ошибки и восстановление понятным языком

Приоритет P1. Состояние: Предложена.

Единый список «нужно внимание»: восстановить черновик, закончить отправку, проверить разрешение, освободить место. Текст сообщает, что сохранено и что делать дальше. Для ручной передачи поддержке предложить диагностический пакет с предварительным просмотром. Существующая политика полного диагностического payload принята владельцем; изменение состава, доступа и срока хранения требует отдельного решения и не включается в эту UX задачу автоматически.

Приёмка: типовые сетевые, дисковые и lifecycle сбои приводят к понятному следующему действию; повторный старт не прячет проблему. Поддержке хватает безопасного ID операции и технических стадий для поиска, координаты и рабочие данные не отправляются без принятой политики.

## UX-05 Напоминание об устаревших данных и обновлении

Приоритет P1. Состояние: В PR #78; адресные emulator/unit/UI проверки пройдены, Full смартфона и планшета ещё выполняется. Владелец — Android app.
Причина: полевые устройства неделями работают без интернета или в авиарежиме.
Зависимости — существующие ProjectSyncState и проверенный self-hosted updater;
нового серверного контракта нет. Полная приёмка смартфона/планшета выполняется
после этого изменения; остальные задачи очереди не запускаются и не расширяются.

Приёмка: более семи суток без успешного полного sync активного онлайн-проекта
и без успешной проверки обновлений различаются. У локального проекта sync не
проверяется. Известное более недели обновление даёт разные сообщения до загрузки
и после проверенной загрузки; новое издание не сбрасывает отсчёт уже ожидающего
обновления. Предупреждение не блокирует работу, не запускает sync/установку само
и не повторяется при повороте/сетевом retry в том же процессе. Неизвестная старая
история получает неделю наблюдения без выдуманной даты успеха. Unit, native UI
в обеих темах/ориентациях и крупном интерфейсе; затем Full на обоих устройствах.

## EXT-01 Кандидаты на расширение функционала

Приоритет P2. Состояние: Идеи для продуктового отбора. Это возможные следующие эпики, а не обещанный состав ближайшего выпуска.

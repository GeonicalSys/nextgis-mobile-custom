# Отчёты об ошибках мобильного приложения

## Долгое получение GPS

Приложение автоматически собирает диагностику, если первое получение GPS долго
не удаётся или после потери свежего положения восстановление затягивается.
В отчёт входят количество видимых и используемых спутников, время последнего
измерения и получения координат, точность, состояние обработки и энергосбережения.
Включать подробный журнал и вручную отправлять файл для этого не требуется.
При отсутствии связи отчёт ждёт отправки в общей очереди. Отключённый пользователем
GPS и отсутствие разрешения не считаются таким сбоем. По одному отчёту нельзя
надёжно доказать работу глушилки: он помогает отличить отсутствие спутникового
фикса от задержки обработки уже поступивших координат.


После установки версии с новой диагностикой отчёты об ошибках отправляются
автоматически. Пароль GlitchTip в телефоне вводить не нужно.

Если интернет отсутствует, приложение сохраняет отчёт на устройстве. После
появления сети повторяет отправку, в том числе фоновым заданием Android.
Запускать синхронизацию проекта специально для этого не требуется. После
падения можно снова открыть приложение и продолжить работу с восстановленным
черновиком. Не удаляйте данные приложения и не переустанавливайте его с очисткой:
это удаляет ещё не отправленные отчёты вместе с другими локальными данными.

Android может отложить фоновую доставку ради экономии батареи. Если приложение
было принудительно остановлено в настройках телефона, откройте его снова.
Очередь ограничена: при очень долгом отсутствии связи старейшие из более чем
256 обычных отчётов могут быть вытеснены.

## Как разбирать присланные ошибки

1. Откройте [багрепорты](https://apps-geonical.ru/errors/) и войдите под учётной
   записью администратора. Данные входа хранятся в согласованной локальной папке
   ServerAdmin/GlitchTip, в файле «Вход в багрепорты.txt».
2. Выберите проект **NextGIS Mobile**. **Setup verification** используется для
   синтетических проверок доставки.
3. Откройте ошибку. Смотрите время события, число повторов, тип и текст ошибки,
   стек вызовов, версию приложения, Android и модель устройства.
4. В тегах `brand` указан бренд, `environment` различает тестовые и рабочие
   сборки, `source_revision` — коммит кода сборки (`+dirty` означает локальные
   изменения), `operation` — последняя операция. Например, AZIMUTH — азимут,
   STAKEOUT — вынос, SYNC — синхронизация. Breadcrumbs показывают последние
   стадии работы и экраны перед ошибкой.
5. После исправления и проверки отметьте ошибку решённой. Новое появление на
   исправленной версии требует повторной проверки.

Приложение не прикладывает скриншоты, ZIP с проектом или полный GPS-журнал.
Сведения, уже попавшие в событие ошибки, сохраняются: сообщения, пути, параметры
запроса, HTTP-заголовки и ответы, значения полей и контекст операции. Пароли и
токены в этих данных не скрываются по требованию владельца системы. Длинные строки
и большие структуры ограничены по размеру. Стек ошибки и сведения о программе
передаются в самом отчёте. Повторяющиеся перехваченные ошибки ограничиваются, чтобы одна проблема
не заполняла список; критические падения отправляются отдельно.

Повторные автоматические HTTP 5xx ограничены десятью минутами в текущем запуске.
`http_status` показывает код ответа, `http_source` — local/remote/unknown,
`http_method` — метод запроса. В Request смотрите URL и Query String, в Response —
код и заголовки ответа. В новых событиях `diagnostics_contract=2` адреса и параметры
сохраняются; удалённые сведения прежних отчётов восстановить нельзя. Например, 503 с local относится
к локальному поставщику тайлов; один такой отчёт не означает падения приложения.
Количество событий теперь показывает допущенные отчёты, а не каждый запрос тайла.

В новых отчётах 503 смотрите local_tile_reason и local_tile_request:
очередь и нехватка памяти различаются явно. map_runtime показывает задержавшийся
запрос, режим карты, загрузку слоёв, последний кадр, память, очередь и этап
обработки тайла. Его собственные version/source_revision относятся к снятому
состоянию, включая старый процесс при delayed ANR. Отчёт можно отметить
обработанным после разбора и подготовки диагностики; это не означает,
что неустановленная причина уже устранена.

Если проблема видна на экране, но исключение не возникло, автоматического отчёта
может не быть. Для такого случая полезны описание действий и существующий пункт
«Поделиться логом» при включённом локальном логировании. Уведомления из GlitchTip
пока отключены: новые ошибки нужно смотреть в веб-интерфейсе.

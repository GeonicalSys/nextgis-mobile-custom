# Ручной прогон ресурсов карты на T40

Главный подтверждённый кандидат на ускорение — обслуживание существующего
дискового кэша тайлов перед каждой новой записью: полный просмотр каталога,
regex для имён, сортировка и повторные `stat` под общей блокировкой. Чтение
геометрии в этом сеансе значительно дешевле. Пользовательское наблюдение о
слабой связи задержки с количеством объектов согласуется с данными. Строгой
проверки зависимости от числа включённых слоёв в этом сеансе нет.

Это разбор диагностического прогона, не исправление производительности, не
обычный benchmark и не подтверждение полного корректного кадра. Нового
долговременного кэша не предлагается и не добавлено. Full/публикация отложены.

## Что записано и проверено

28 октября, примерно 21:26–21:45 по Europe/Warsaw: пользователь самостоятельно
двигал карту и менял масштаб на T40 Plus/API30. App-session длилась
1140,754 с; лёгкий внешний sampler — 1146 с. Пользователь закончил раньше
плановых 30 минут: получены три окна CPU/native по 180 с, а не пять.
Один процесс PID2474, перезапусков в записанном сеансе нет.

- Сбор штатно остановлен по пользовательской команде; собственные native/CPU
  процессы отсутствуют, light sampler подтвердил остановку. При этой операции
  force-stop/clear приложения не выполнялись. Возврат обычного APK после
  выгрузки описан отдельно ниже; пользовательские данные не очищались.
- App JSONL: 14 054 760 байт, 23 270 записей, SHA256
  `19f44010f6c68d9460fea20be45565f604405d1bfb94c3a16d4393fe0fce39ea`.
  Полный `app_end`, все 19 707 raw запросов независимо совпадают с footer по
  counts/wall/CPU/unknown arrays. Потери очереди/файла, observer/clock/sink errors — 0.
- 1068 memory records, 214 PSS probes, 908 SDK frame summaries, 38 checkpoints.
  Внешний sampler: 211 CPU snapshots, 71 memory snapshots; первая проба

## Подготовка тайлов: затраты и очередь

В таблице — сумма CPU синхронных измеренных фаз за весь сеанс, не секунды
ожидания пользователя и не доли CPU всего приложения. CPU `io_queue`
**полностью исключён**: same-TID counters через coroutine suspension/отмену
могут захватывать чужую работу этого потока и давать двойной счёт. Raw значения
сохранены как свидетельство ограничения сборщика, не используются для рейтинга.
Перед следующим использованием такого показателя wait/suspend phases должны
становиться CPU-unknown; совпадения TID недостаточно.

| Фаза | Известный CPU, с |
|---|---:|
| Запись тайла, включая обслуживание каталога кэша | 551,69 |
| Применение стиля | 39,20 |
| Чтение атрибутов SQL | 17,33 |
| Чтение BLOB | 11,78 |
| Подписи полигонов | 7,02 |
| Декодирование геометрии | 2,73 |

`cache_write` занимает 85,8% CPU всех измеренных фаз после исключения очереди.
Это не 85,8% всего процесса: SDK renderer, драйвер, GC и профилировщики имеют
собственные затраты. Фаза оборачивает `disk.put()` и проверку актуальности;
запись задерживает возврат тайла в SDK и выполняется под блокировкой слоя.

Из 19 707 запросов отменены 13 986 (70,97%), отданы SDK4628, завершены отдельным
provider result1093, failed/abandoned0. Медиана ожидания очереди среди отданных
тайлов — 1,93 с, p95 — 8,59 с. Отмена сама по себе штатна при быстрых движениях,
но такой объём и задержки указывают на важность актуальности/дренирования очереди.
Суммарный wall `io_queue` 31 624 с перекрывается между запросами: нельзя
превращать его в длительность сеанса, CPU или процент пользовательского ожидания.

В `LocalVectorTileDiskCache` один static `DISK_LOCK` используется для read/put.
Каждый новый `put`, включая 17-байтовый пустой PBF, вызывает `prune()`:
`listFiles`/`isFile`/`String.matches`, полную `Arrays.sort` с повторными
`File.lastModified`, затем проход `File.length`. Работа зависит от всего
каталога, а не только от объектов нового экстента; сортировка выполняется
даже когда фактически удалять ничего не требуется.

Независимые native стеки подтверждают этот путь: во втором/третьем окнах весь
`prune` создаёт около 1985/2109 МиБ временных native allocations, 30,7/35,0%
всего наблюдаемого потока. В CPU `File.getLastModifiedTime0` виден как
4,1–6,0%, regex compilation — 7,4–8,1% inclusive. Regex используется и
наблюдателем; его CPU-доли между источниками полностью не разделены.

## Память

Значения в МиБ; максимумы разных показателей могут относиться к разным моментам.
Java/native/RSS наблюдались примерно раз в секунду, PSS — раз в5с.

| Показатель | Медиана | Пик | Конец |
|---|---:|---:|---:|
| Общий PSS процесса | 456,6 | 553,8 | 452,0 |
| Занято в native allocator | 220,2 | 360,2 | 218,0 |
| Занято в Java heap | 35,3 | 108,8 | 16,6 |
| SDK buffers | — | 76,6 | 25,8 |

RSS пик825,7/конец602,4 МиБ. SDK textures около1,27 МиБ. SQLite по независимым
`dumpsys` probes около5,8–7,2 МиБ. Это разные, частично перекрывающиеся виды
памяти: их нельзя складывать, а cumulative update bytes SDK не являются RAM.
Graphics stats всегда0 и не дают пригодного измерения памяти GPU.

Основной большой блок — native память. Java после раннего пика уменьшается;
она не выглядит главным устойчивым владельцем в этом сеансе. Точное владение
всей native/PSS памятью конкретными слоями ещё неизвестно. Около53% native
allocation traffic имеет оборванный стек MapLibre `operator new`; назвать
внутренний объект только по этому стеку нельзя.

За три180-секундных окна оценён поток allocations2177/6461/6033 МиБ,
примерно12,1/35,9/33,5 МиБ/с. К концу каждого окна из видимых после attach
выделений остаётся113/127/126 МиБ; освобождается95–98% потока. Это большой оборот
временной памяти, не такое количество одновременно занятой RAM и не доказанная
утечка. Остатки разных окон не складываются. В двух рабочих окнах названный
`prune` даёт~1,9–2,1 ГиБ этого оборота, особенно regex и JNI/stat/sort.

## SDK и влияние самой диагностики

MapLibre renderer остаётся крупным потребителем:25,5–33,7% user-CPU samples
inclusive; GeometryTileWorker::parse —2,1–8,2%, symbol placement —3,8–7,2%.
Vendor Mali symbols отсутствуют. Эти категории перекрываются; доли нельзя
складывать и нельзя называть временем GPU/ожидания.

Native heap hooks heapprofd присутствуют в22,7/32,4/32,6% CPU samples трёх
окон. Writer thread —4,50/2,65/2,54%. Собственные app observer clocks дают
36,96 CPU-с за сеанс, около2,04% CPU процесса; это не все расходы диагностики.
Независимый `/proc` sampler даёт1800,90 CPU-с за1134,72с между пробами, из них
1213,02 user/587,88 kernel;100% означают одно полностью занятое ядро.
Heapprofd доля inclusive включает дочерние вызовы, часть которых существовала
бы и без hooks; это не измеренная прибавка к обычному времени. Вычитать этот
процент из задержки и обещать соответствующее ускорение нельзя.

После исключения ±5с вокруг границ тяжёлых окон медиана/p95 `cache_write` CPU
в них189/450мс, в промежутках114/128мс; wall252/756 против117/235мс. Участки,
плотности и движения различаются, поэтому это не A/B и не оценка точного
замедления профилировщиком. Но профилирование явно существенно: обычную скорость
или будущие2–3с этим прогоном не подтверждаем. При этом дорогая операция видна
и в промежутках без native profiler.

## Приоритет следующей проверки/оптимизации

1. Убрать полный scan/regex/sort/stat каталога из горячего пути каждого `put`:
   ограниченный учёт размера/числа записей и редкая bounded очистка, без общей
   блокировки на длительное обслуживание. Сохранить текущие budgets, атомарную
   публикацию PBF, generation/style identity, безопасный miss и источник SQLite.
   Это устранение накладных расходов существующего кэша, не новый долговременный кэш.
2. Проверить отмену и приоритет актуального viewport: ненужные запросы не должны
   задерживать новые и проходить до дорогого `put`; независимые регрессии обязаны
   сохранить actual feature/label contents при резких17→12/new-extent переходах.
3. Исправить CPU атрибуцию wait/suspend фаз и удешевить observer validation;
   следующий тайминг с CPU-only/лёгким observer, native heap — отдельно короткими
   окнами. Повторить релевантные экстенты и плотности; Full этим не разрешается.
4. После устранения общего bottleneck повторно разобрать MapLibre parse,
   symbol placement/перестройку buffers и неизвестных native владельцев.

Эти оптимизации в данном разборе не реализованы. Обещания2–3с пока нет.
